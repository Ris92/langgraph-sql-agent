Graph Node Reference
====================

| Node             | What it does                                          |
|------------------|-------------------------------------------------------|
| first_tool_call  | Kicks off the pipeline by listing tables              |
| list_tables_tool | Executes the sql_db_list_tables tool call             |
| model_get_schema | LLM picks which tables to fetch schemas for           |
| get_schema_tool  | Executes the sql_db_schema tool call                  |
| query_gen        | LLM writes SQL, then on 2nd pass submits final answer |
| correct_query    | LLM validates the SQL query                           |
| execute_query    | Runs db_query_tool with the validated SQL             |

Fix 4: Programmatic guard in query_gen_node (Cell 9)
-----------------------------------------------------
Root cause: prompt instructions alone were insufficient — GPT-4o still called
SubmitFinalAnswer without executing a query when the answer was visible in the
schema sample rows (e.g. ArtistId 1, 2, or 3).

Fix: Added a code-level guard inside query_gen_node. When SubmitFinalAnswer is
called, the guard checks state["messages"] for any prior ToolMessage from
db_query_tool. If none exists, it returns an error message forcing the LLM to
write a SQL query first. This enforces the rule in code rather than relying on
the LLM to follow instructions.
Old query_gen_node commented out with "claude made the change" marker.

appears twice, with correct_query and execute_query in between.

Step 3 (continued) — Fix 5: Max retry limit in query_gen_node (Cell 9)
========================================================================

Root cause: if the agent keeps producing bad SQL that execute_query rejects,
the loop between query_gen → correct_query → execute_query → query_gen has
no exit condition and can run forever.

Fix: Added a retry counter to query_gen_node using the LangGraph state dict.
- Added MAX_QUERY_RETRIES = 5 constant (Cell 9)
- At the start of query_gen_node, reads state.get("query_retry_count", 0)
- If retry_count >= MAX_QUERY_RETRIES, skips the LLM call entirely and
  returns a SubmitFinalAnswer with a clear failure message
- If an error ToolMessage is generated (meaning a retry will happen),
  increments query_retry_count by 1 in the return dict
- On a clean pass (no errors), leaves the count unchanged
